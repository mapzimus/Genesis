## Finding 1 — wrong model (blocking)

Both fired sessions served `claude-sonnet-5`. The protocol fixes `claude-fable-5` at `high` effort as a preregistered condition, and the repository pins it in both `.claude/settings.json` and `STATE.json`. The Routine's own session configuration takes precedence over the repository setting, so a scheduled cycle would run on the wrong model.

This is material rather than cosmetic: the research question asks what **one consistently configured Claude agent** achieves. Cycles alternating between the director's model and the scheduler's default would invalidate that condition and, under `prompts/EVALUATOR.md`, would surface as an unreconstructable model history.

Status: `UNRESOLVED`. The Routine model cannot be changed on the director's own initiative; it requires Max's explicit instruction or recreation of the Routines with the model set.

## Finding 2 — no connectors in fired sessions (blocking, confirmed)

The connector gap recorded at Routine creation is confirmed by configuration: each Routine's stored `allowed_tools` list contains no `mcp__github__*` entries. A fired session therefore cannot read `approval-request` issues, transcribe owner decisions, post a `daily-report`, or open an `incident` issue. Git over HTTPS is unaffected, so records could still reach `main`, but the approval path in `CLOUD_ENVIRONMENT.md` would be unavailable to exactly the sessions that need it.

Status: `UNRESOLVED`.

## Readiness consequence

`operator_schedule_tested` and `close_schedule_tested` remain **false**. The cycles behaved safely, but the configuration exercised is not the configuration the experiment requires: wrong model, and missing the connectors the communication design depends on. Both dry runs must be repeated after the Routines are corrected, and only then may the flags be set true.

The dry runs did their job. They were run precisely to surface this class of defect before Day 1, and they surfaced two.
